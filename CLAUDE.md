# security-gym

Gymnasium-compatible environment that replays labeled Linux log streams for continual learning research.

See `ROADMAP.md` for project phases and `TODO.md` for current action items.

**Terminology (settled 2026-08-19)**: describe security-gym as a trace-driven replay environment, never a simulator. The telemetry is recorded and replayed; no dynamics model generates it. The only simulated component is the defense layer (blocklist, throttle list, isolation mode), so the loop is closed on observability but not on adversary behavior: blocking suppresses an attacker's events, but the recorded attacker never changes tactics. Reserve "environment" for the software and its Gymnasium API, "corpus"/"dataset" for the released v4.1 data, and "benchmark" for the evaluation protocol plus baseline results (not as a nickname for an individual stream). Canonical wording is in README.md's opening two paragraphs, mirrored in `data/HF_DATASET_CARD.md`.

## Architecture

- `src/security_gym/` — installable package (`pip install -e .`)
- `attacks/` — attack scripts for data generation (NOT pip-installed)
- `campaigns/` — YAML campaign configs for Isildur (ssh_brute_only, log4shell_only, recon_only, recon_ssh_log4shell, credential_stuffing_only, post_auth_only, full_killchain, redis_exploit_only, redis_killchain)
- `configs/` — YAML composition configs for StreamComposer (stream_7d_brute_only, stream_30d_heavy, stream_90d_mixed, stream_365d_realistic)
- `server/` — target VM provisioning docs, Docker Compose for vulnerable services, and eBPF collector daemon
- `data/` — runtime data directory (gitignored)
- `tests/` — pytest test suite

## Key Patterns

- **Parsers**: decorator-based registry (`@ParserRegistry.register('auth_log')`); six parsers: `auth_log`, `syslog`, `web_access`, `web_error`, `journal`, `ebpf`. Shared syslog header in `_syslog_header.py` with `parse_syslog_header()` supporting both BSD (`Feb 22 00:55:01`) and RFC 3339 (`2026-02-22T00:55:01.662021-05:00`) timestamp formats; RFC 3339 offsets are converted to UTC. All parsers store `event_type` in `fields["event_type"]` for DB round-trip. EventStore also injects `event_type` into the parsed JSON as a safety net if a parser omits it. The `auth_log` parser is stateful — it caches PID→(src_ip, session_id) from auth events to enrich PAM session open/close events that lack IP/port info.
- **EventStore**: SQLite with WAL mode, ID-based cursor for resumable reads. Schema version 2. Valid sources: `auth_log`, `syslog`, `web_access`, `web_error`, `journal`, `ebpf_process`, `ebpf_network`, `ebpf_file`.
- **Environment**: a single environment family with two registered observation modes. Both share the action space, reward structure, defense state, and continuous-stream semantics; they differ only in how the eBPF channels are encoded.
  - **Action**: `Dict` of `Discrete(6)` (pass/alert/throttle/block_source/unblock/isolate) + `Box(1)` risk_score (0-10, GVF-like auxiliary prediction) + `Discrete(target_slate_size + 1)` target (0.6.0).
  - **Target selection (0.6.0, default `target_slate_size=64`)**: `target` names the address an action applies to. 0 is the current event's source (the only binding before 0.6.0); 1..N name a slot in the target slate, an observable list of addresses seen anywhere in the stream. Exists because 93.5% of `exp_30d_heavy_v4` events carry no address (99.9% of those are eBPF; an `openat` has no peer address), so binding to the current event forecloses acting on kernel evidence. Slate slots are stable; eviction is least-recently-seen among *uncontrolled* addresses, and blocked/throttled addresses are pinned, which is what keeps a blocked host nameable for release under `"drop"` visibility. If every slot is pinned, new addresses are reachable only via target 0. Rendered as a numbered text channel (`target_slate`) in text mode and `Box(N, 3)` = `[addr_hash, is_blocked, is_throttled]` in hybrid, hashed with `SEED_IP` so a slot and a `network_events` row agree on a host. Implemented in the base env (`_observe_address`, `_resolve_target`, `_render_target_slate`, `_target_slate_matrix`); hybrid duplicates `reset`/`step` so the slate feed is wired in both.
  - **Reward**: asymmetric action costs (block benign = -1.0, block attacker = +1.0, pass benign = 0.0) + risk score MSE + ongoing consequence feedback from blocked/throttled events. Two rules added in 0.6.0 (`_action_reward`): an address-taking action that changed no state scores 0.0 rather than being paid in full (this is the common case, not the corner case, since ~93.5% of steps carry no address), and an explicitly targeted action is graded on the target's last observed label rather than the current event's, falling back to the current event when the address has never been seen labeled. Grading is causal: it uses only labels already shown to the agent. **`include_risk_reward` defaults to `False`** (commit a5ceae9), so the risk-MSE term is dormant unless enabled; the pre-0.6.0 README baselines table was generated before that flip and its mean-reward column described a reward the env no longer computed.
  - **Defense state**: blocklist (100% drop), throttle list (90% drop), isolation mode (blocks all network events). Agent can escalate/de-escalate: throttle → block → unblock.
  - **Block recovery (opt-in, default-off, 0.5.0)**: two composable constructor params make the block→unblock loop learnable (default behavior — permanent 100% invisible block — is preserved byte-for-byte). `block_visibility="deny_log"` (default `"drop"`) still drops a blocked IP's events at the firewall but surfaces each as a ground-truth-blind `"[FIREWALL DENY] "` line so an explicit `unblock` on that IP becomes reachable (no `is_malicious` leak into the observation). `block_ttl` (event-seconds, default `None`) auto-expires a block fail2ban-style; the IP re-surfaces for re-decision. Implemented in the inherited `_advance`/`_apply_action`/`_compute_reward` (so both envs inherit; hybrid threads the params and mirrors the reset state). Reward accounting: a surfaced deny-log step contributes only the consequence term (action+risk zeroed) to avoid double-counting; episode-total consequence is unchanged from drop mode (only redistributed across steps). Scope: governs the 100%-block path only (not isolation/throttle); hybrid structured eBPF channels carry no deny marker, so the deny annotation shows only in text channels.
  - **Defense state observation (opt-in, default-off, 2026-08-19)**: `defense_state_obs=True` adds a `defense_state` channel reporting the agent's own control state, which the observation otherwise omitted entirely (it was reachable only via the `info` dict, alongside the ground-truth labels). Text mode renders operator-style status output (`=== defense state ===`, blocked/throttled address lists capped at `DEFENSE_STATE_MAX_LISTED`, isolation, `events_suppressed`, `seconds_since_change`, and a `current_src` line marking the current event's IP `[BLOCKED]`/`[THROTTLED]`); hybrid mode encodes `Box(DEFENSE_STATE_COLS=6)` = `[n_blocked, n_throttled, is_isolated, current_src_blocked, current_src_throttled, seconds_since_last_change]`, dropping the address list since it has no fixed-width form. Implemented in the base env (`_render_defense_state`, `_defense_state_vector`, `_stamp_defense_change`, `_seconds_under_current_state`) so both envs inherit; hybrid threads the param and mirrors the reset state. Ground-truth-blind by construction: every field is a consequence of the agent's own actions. Default-off preserves the legacy observation space byte-for-byte; whether it becomes the published default is open (TODO.md "State Space"). `_stamp_defense_change` fires only on an actual state change (including `block_ttl` expiry), not on every action.
  - **Continuous stream**: `terminated=False` always, `truncated=True` at end of data.
  - **Text mode (`SecurityLogStream-Text-v0`)**: `Dict` of 6 `Text` channels (`auth_log`, `syslog`, `web_log`, `process_events`, `network_events`, `file_events`) + `Box(3)` system stats. Ring buffer per channel (configurable `tail_lines`, `max_chars`). Agent reads raw text (like `tail -N` of log files and kernel event channels).
  - **Hybrid mode (`SecurityLogStream-Hybrid-v0`)**: log channels (auth_log, syslog, web_log) remain `Text`; eBPF channels (process_events, network_events, file_events) become fixed-width `float32` `Box` arrays with mmh3 hashing for string fields. `system_stats` unchanged. Reflects real SOC tooling where kernel telemetry arrives as structured data. ROADMAP.md Phase 13 covers planned `lsm_events` channel and process-tree depth enhancements.
  - **Legacy aliases**: `SecurityLogStream-v1` and `SecurityLogStream-v2` were registered as deprecated aliases in 0.4.0 and removed in 0.4.1. Code referencing the old IDs must update to `SecurityLogStream-Text-v0` and `SecurityLogStream-Hybrid-v0`.
- **eBPF Collector**: `server/ebpf_collector.py` — BCC daemon attaching to kernel tracepoints (execve, connect, accept, openat, unlinkat). Deployed on Isildur (Debian 11, kernel 5.10, BCC 0.18) and 3 Debian 13.4 servers (frodo, 9600baud, hopper — BCC 0.31). Output: timestamped text lines with enriched fields — process events include `ppid` + `parent_comm` (via `task->real_parent`), network events include `uid`. Self-PID filtering to avoid feedback loops. Orchestration wrapper: `attacks/collection/ebpf_collector.py` (paramiko Ed25519 SSH transport with keepalive).
- **Adapter**: `SecurityGymStream` reads EventStore directly, maintains ring buffers per channel (same as env), yields text observations + ground truth dicts. Supports `speed` (0=full, 1.0=realtime, 10.0=10x) and `loop` (never-ending wrap-around) parameters.
- **StreamComposer**: offline composition of benign + attack EventStore DBs into experiment streams (`data/composer.py`). Handles both log and eBPF events (all use same events table). YAML config specifies duration, seed, Poisson attack schedule (`campaigns_per_day`), and MITRE ATT&CK-weighted type distribution. Cycles benign events to fill duration, transplants attack sessions preserving intra-session timing. Deterministic given seed.
- **Registration**: belt+suspenders — `__init__.py` calls `register_envs()` on import AND `pyproject.toml` entry point for auto-discovery
- **Attack Modules**: decorator-based registry (`@AttackModuleRegistry.register('ssh_brute_force')`); six modules: `recon` (scapy SYN scan), `ssh_brute_force` (paramiko), `log4shell` (requests + JNDI injection), `credential_stuffing` (paramiko, unique cred pairs tried once each), `ssh_post_auth` (paramiko, post-auth command execution with 4 command profiles + optional payload download), `redis_lua_escape` (raw TCP/RESP, CVE-2022-0543 Lua sandbox escape via `package.loadlib()` for unauthenticated RCE — 3-stage: enumeration, exploitation, post-exploitation with 6 command profiles). Non-stationary `TimingProfile` with constant/accelerating/decelerating/custom profiles. Kill chain campaigns: recon → credential stuffing → post-auth execution; recon → Redis exploit → SSH pivot.
- **Campaign Framework**: YAML-driven orchestrator — load config → start eBPF collector (if enabled) → execute phases → stop eBPF → SSH collect logs → label (time+IP matching) → bulk insert into EventStore. CLI: `python -m attacks run/validate/list-modules/compose`. eBPF collection configured via `collection.ebpf.enabled: true` in campaign YAML. eBPF events are routed through the same `CampaignLabeler` as log events (time+IP matching), so kernel events during attack windows are labeled malicious by window membership; this misattributes kernel events in both directions (see Known eBPF Data Validity Issues, defect 7).
- **Label Validation**: `scripts/validate_labels.py` — 9 checks (label consistency, raw line spot-checks, campaign boundaries, campaign type cross-val, target array NaN masking, attack type distribution, temporal order, no unlabeled events, session coherence). Supports `--check NAME` to run subset, `--spot-check N`, `--sample-size N`, `--verbose`. Exit 0 = all pass/skip, exit 1 = any FAIL. Distribution check is WARN-only (campaign weights control frequency, not event count — brute_force generates ~40x more events per campaign than discovery).
- **Deprecated (v0)**: Feature extractors (`features/extractors.py`, `features/hasher.py`, `features/session.py`), wrappers (`envs/wrappers.py`), and target builder (`targets/builder.py`) are retained for backwards compatibility but no longer used by the v1 environment. The agent now learns its own representations from raw text.
- **Data Versions**: v1 databases (`benign.db`, `campaigns.db`) contain log events only. v2 databases (`benign_v2.db`, `campaigns_v2.db`) added eBPF kernel events. **v3 database** (`benign_v3.db`) is a clean rebuild from personal server logs (no hospital PII). **v4 database** (`benign_v4.db`) adds 3.24M benign eBPF events from 3 servers (frodo, 9600baud, hopper) to the v3 base — 11,159,241 total events (7.9M logs + 3.24M eBPF). Built via `scripts/build_benign.py` which accepts server log tarballs containing auth.log, syslog, nginx, or apache2 logs, and supports `--base-db` for incremental builds (copy existing DB, process sources for IP accumulation only, then append eBPF). Malicious traffic (SSH brute force, scanner probes, SQLi, XSS, JNDI) is automatically filtered; the `MaliciousFilter` also accumulates attacker IPs from filtered auth/web events and uses them to filter `ebpf_network` events during eBPF carryover. PII (hostnames, domains, IPs) is scrubbed to match the campaign target server (`isildur` / `192.168.2.201`) so all benign + attack data appears to come from one host. Scrubbing is configurable via JSON config (`--scrub-config`) or disabled with `--no-scrub`. Multiple `--ebpf-source` DBs can be specified (one per server). Build report at `data/build_benign_report.json` (includes `ebpf_events_filtered` count and SHA256 hash). Composition configs and experiment streams now use `benign_v4.db`.
- **eBPF Baseline Collections** (2026-03-22): 24-hour collections from 3 Debian 13.4 servers — frodo (2,355,832 events, `data/ebpf_frodo.db`), 9600baud (785,473 events, `data/ebpf_9600baud.db`), hopper (102,078 events, `data/ebpf_hopper.db`). Total: 3,243,383 benign eBPF events. Integrated into benign_v4.db via `--base-db` mode.
- **Known Data Quality**: campaigns.db has 87 temporal order violations (multi-server import boundary) and 6 mixed-label sessions (labeler edge cases). campaigns_v2.db has 60,468 events (30,436 malicious, 30,032 benign) across 10 campaign IDs (including Redis CVE-2022-0543); 24 temporal order violations and 3 mixed-label sessions. Composed experiment streams are clean — StreamComposer sorts by timestamp. **benign_v3.db has zero temporal order violations** — the build script sorts all events by timestamp after multi-server merge. Check 2 (raw line spot-checks) fails on eBPF events because the spot-checker can't pattern-match kernel event lines (file opens, accepts, exits) — these are labeled by time+IP window matching, which the 2026-11-07 audit found unreliable for kernel events (defect 7 below). **Note:** Existing v2 databases were generated before the event_type/session-enrichment fixes; re-composing will pick up the fixes for newly parsed data, but already-serialized events in campaigns_v2.db and benign_v2.db retain the old parsed JSON.
- **Campaign Corpus Characteristics (audited 2026-08-09)**: the 10 campaign IDs in campaigns_v2.db come from 9 YAML configs; `recon_only` ran twice and the first run (`campaign_f1e3fd24735f`) was aborted after 18 seconds with 0 attempts and 1 event, so exclude it. Total wall-clock capture is roughly 75 minutes across two sessions (eight campaigns 2026-03-01 22:00-23:04 UTC, two Redis campaigns 2026-03-06 18:20-18:31 UTC); StreamComposer replays this into the multi-day streams. Outcomes are deterministic: credential attacks never succeed (0/76 brute-force, 0/50 stuffing, since the credential lists are fabricated) while exploitation always does (350/350 Log4Shell, 4/4 Redis, 6/6 post-auth with valid credentials), so there are only 8 `Accepted password` lines in the whole corpus and no partial or failed exploitation. Kill-chain phases advance on a timer, not on the prior phase succeeding. The ~30k benign events are target-host background and measurement apparatus captured in the same window, not a benign baseline (the BCC collector compiling its BPF program accounts for 7,639 of 19,456 benign `ebpf_file` events); the real baseline enters from benign_v4.db at composition. Known mislabel: `full_killchain.yaml` and `redis_killchain.yaml` tag the recon phase `TA0043` (Reconnaissance) while `recon_only`/`recon_ssh_log4shell` tag the identical T1046 SYN scan `TA0007` (Discovery); T1046 is a Discovery technique, so the TA0043 values are wrong. The README table is correct; the YAMLs and the shipped `mitre_tactics` column are not. `attack_type`/`attack_stage` (used for training) are unaffected. Per-campaign counts and limitations are documented in `data/DATASET_README.md`; config list in README.md "Campaign Configurations".
- **Known eBPF Data Validity Issues (under investigation, 2026-06-05; ROADMAP/TODO Phase 14, BLOCKED)**: The benign eBPF in benign_v4.db and the composed v4 streams has seven defects that threaten the eBPF ablation (Exp 13: 60% MAE reduction, Cohen's d=2.577); defects (1) to (3) are composer/build-pipeline issues found 2026-06-05, (4) to (5) are collector bugs found 2026-08-09 that affect every eBPF collection to date, and (7) is a labeler defect found 2026-11-07. (1) Sessionization asymmetry: kernel events have no native session; the composer assigns a synthetic per-campaign session to attack eBPF only (`data/composer.py:226-237`, keyed on the attacker IP), while benign eBPF stays NULL (process and file events also lack `src_ip`), so a session-level scorer can separate the two on key structure alone (label leakage). (2) Cross-server PID collision: `scripts/build_benign.py` merges eBPF from frodo, hopper, and 9600baud with unnamespaced `pid`/`ppid`, corrupting the `tree_depth` ancestry feature (`envs/log_stream_env_hybrid.py:167-170`) for benign events while single-host attack campaigns retain valid chains, confounding "ancestry helps" with host-of-origin. (3) Distributional realism: three heterogeneous hosts stacked and timestamp-cycled do not reflect any single host's kernel distribution. (4) Byte-reversed IPv4 addresses on `ebpf_network` `connect` events. **Collector fixed 2026-08-28; all shipped data still carries the defect.** `_ip_str` packed a host-byte-order value as network byte order, so `dst=3.0.18.172:8080` is really `172.18.0.3` (the port on the same line was always correct, since it uses the complementary pack-native/unpack-big-endian idiom). Root cause: `bpf_probe_read_user` copies the raw network-order bytes of `sin_addr` into a `u32` and BCC decodes that field natively, so the value reaches Python already host-ordered; packing it `"!I"` swapped a second time. The fix is `struct.pack("=I", addr)`, correct on either host endianness. The parser derives `src_ip` from this field (`parsers/ebpf.py:87-89`), so the corruption reaches labeling and the env's IP-keyed blocklist, where it splits one host into two identities (`192.168.2.20` in auth_log against `20.2.168.192` in the network channel) and makes any cross-channel per-IP containment metric wrong. Data collected before 2026-08-28 is unaffected by the fix and must be read with the octets reversed; evidence and per-artifact counts in `data/provenance/EBPF_IP_BYTE_ORDER_20260828.md`. (5) `accept` events carry no peer address: `sys_enter_accept4` never reads `upeer_sockaddr` (`server/ebpf_collector.py:156-166`), which needs an entry/exit probe pair since the kernel fills the address on return; in campaigns_v2.db all 619 malicious `ebpf_network` events are addressless `accept`s and all 603 addressed events are benign `connect`s, so the network channel holds no correctly-addressed malicious event and those labels rest on time-window matching alone. (6) Address presence on kernel events is a perfect label (2026-08-28, a fourth manifestation of defect 1): in `exp_30d_heavy_v4`, 499,084 of 499,084 addressed `ebpf_file` events and 16,841 of 16,841 addressed `ebpf_process` events are malicious, against 2.74% for `ebpf_network` (stream base rate 2.83%). The composer stamps the attacker IP onto attack eBPF only, and file/process events have no native address, so "has an address" means "is an attack". Not rendered in those channels directly, but it feeds the 0.6.0 target slate, so slate recency and eviction correlate with attack activity; kernel-channel targeting results are not clean until the symmetric session fix lands. (7) Window-based labeling misattributes kernel events in both directions (audit 2026-11-07, `data/provenance/KERNEL_LABEL_AUDIT_20261107.md`): `CampaignLabeler` (`attacks/collection/labeler.py:120-127`) labels addressless events on the time window alone and addressed events only if the address is an attacker's. In campaigns_v2.db, 86 of 602 addressed `ebpf_network` events are unambiguously attack-caused yet labeled benign (80 Log4Shell `java` JNDI callbacks failing the address test through defect 4, 6 `wget` lookups to `8.8.8.8:53` that no address test can catch), and the composer's `is_malicious = 1` filter (`data/composer.py:142`) keeps them out of every composed stream; meanwhile 22.70% to 47.56% of malicious kernel events per channel are system-service reactions (`systemd*`, `dbus-daemon`) of unsettled attribution, and up to 0.51% are unrelated background (`cron`, `tmux:`, `systemd-udevd`). `validate_labels.py` passes because none of its checks is semantic; the audit's Handoff Brief lists the recommended order and acceptance checks, and the corpus policy (relabel, drop, or document) is undecided. Log-only results (session F1 0.979) are unaffected by (1) to (6); (7) reaches the log channels only marginally (5 of 350 Log4Shell `web_access` requests labeled benign, 1.43%). Diagnose-first plan and re-collection options are in Phase 14; do not treat the eBPF ablation as settled until the diagnostic re-run is complete.
- **Action-Space Control Semantics (defect found by audit 2026-08-19; addressed in 0.6.0, 2026-08-28)**: the discrete action was graded but frequently inert, so the environment behaved as a per-event classifier with a reward table rather than a control problem. `_apply_action` bound throttle/block/unblock to the current event's `src_ip`, and `_compute_reward` graded from the ground-truth label alone without checking that the defense state changed. Measured: 93.50% of `exp_30d_heavy_v4` events (20,112,710 of 21,511,208) and 95.40% of `exp_7d_brute_v4` events have NULL `src_ip`; 99.9% of those are eBPF and `ebpf_file` alone is 94.6% of them, so this is structural (an `openat` has no peer address), not a parsing gap. Within the 30-day stream 72,409 malicious events (11.88%) paid block's +1.0 with no containment and 20,040,301 benign events (95.88%) paid -1.0 for dropping nothing. Fixed by target selection (see Environment above) plus the reward-effect rule; `unblock` is now reachable under default `"drop"` because controlled addresses are pinned in the slate. Still open: `isolate` remains absorbing (`_is_isolated` is cleared only by `reset()`) on a stream where `terminated` is always False, and the `Box(1)` risk score remains unrewarded by default (`include_risk_reward=False`). Remaining items in TODO.md under "Action Space — Control Semantics".
